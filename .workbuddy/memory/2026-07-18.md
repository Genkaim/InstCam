1. `_shutterFlash.tryEmit(Unit)` → 白闪
2. `_photoCaptured.emit(file)` → 过渡立即开始（Morph+Extend，无照片）
3. 后台 `addPolaroidFrame(file)` 写白框
4. `showPhoto = true` → AsyncImage 加载磁盘文件（已是 Polaroid 版）
5. Emit → 打印出带白框的照片
6. Grow → 照片放大到中央预览
7. Shrink → 灵动岛缩回正常尺寸
8. **`onAddToAlbum`**: `setPlaceholder` + `refreshPhotos` → 相册首位**透明**占位（`Color.Transparent`，无可见元素）
9. 用户退出 → `close()` 飞入占位 → `clearPlaceholder` + `refreshPhotos` → Polaroid 照片出现在相册

**注意：** 背景不再 `refreshPhotos`——相册在整段动画期间没有任何变化。

## 第四轮修复：相册性能 + Polaroid 缓存

### 问题
1. 相册照片多时 LazyVerticalGrid 卡顿——`SubcomposeAsyncImage` 每格都调用 `painter?.intrinsicSize` 导致 layout shift，且以全分辨率解码
2. 连续快速拍照时，相册缩略图显示的是**原始 JPEG**（无白框），点进详情却有白框；重启 App 才正常——Coil 内存缓存 key = `file.path`，addPolaroidFrame 修改文件后 key 不变，缓存命中旧版本

### 修复方案

**`CameraViewModel.kt`**：
- 新增 `_photoVersion: MutableStateFlow<Long>` + `.asStateFlow()` 公开 `photoVersion`
- `refreshPhotos()` 在更新 `_photos` 后同时递增 `_photoVersion = System.currentTimeMillis()`

**`CameraScreen.kt` — GridPhotoCard**：
- 新增参数 `photoVersion: Long`

- `SubcomposeAsyncImage` 改用 `ImageRequest.Builder`：

  - `.memoryCacheKey("thumb_${file.path}_$photoVersion")` → 版本变则 key 变，缓存失效，强制加载 Polaroid 版
  - `.crossfade(300)` → 加载完成 300ms 淡入

**`CameraScreen.kt` — 占位**：
- 相同优化：预读比例 + `ImageRequest` + 版本 key + crossfade

### 效果
- 缩略图始终稳定比例，`LazyVerticalGrid` 无反复 layout shift → 丝滑滚动
- 拍完照 `refreshPhotos()` 后 `photoVersion` 递增 → 所有单元格 memory cache key 变化 → 回源读磁盘（此时文件已是 Polaroid 版）→ 缩略图正确显示白框

## 第八轮修复：GridPhotoCard 无动画拍照时 1:1 比例 bug

### 问题
关闭"开启动画"开关时，拍照后相册第一张照片显示为 **1:1**（而不是原图 4:3 或带白框后的实际比例）。

### 根因分析（关键：不是延迟问题，是写入时序问题）
1. `takePhoto` 中 `addPolaroidFrame(file)` 在 IO 协程里跑：读原图→旋转→滤镜→加白边→`FileOutputStream(file).compress(JPEG, 95)` 覆盖写回原路径（**写过程中文件被截断**）
2. 同时 `photoCaptured.collect` 无动画分支**立即**调 `vm.refreshPhotos()` → `_photos` 立即含新文件
3. `GridPhotoCard` 第一次渲染执行 `remember(file) { BitmapFactory.decodeFile(...) }`，此时 addPolaroidFrame 还在写文件 → decode 失败 → `outWidth=0` → 走 `else 1f` → **1:1**
4. 之后 `_photoVersion` 更新但 `remember(file)` 不重算（key 只有 file），**永远卡在 1f**

**Overlay 没事**因为它在 Extend 完成后**等 `photoVersion` 变化**才 `showPhoto=true`，那时 addPolaroidFrame 已写完。

### 修复方案（写入完成才入列，不靠延迟）
- **`CameraViewModel.takePhoto`**：`addPolaroidFrame` 完成后**才** `listPhotos` + 更新 `_photos` + 更新 `_photoVersion`

## 第十三轮：灵动岛偏下 + 预览顶部渐变 + 退出预览背景残留

### 问题

2. **打印动画之后，预览照片画面顶部有突兀的渐变**
3. **退出预览照片之后，平滑过渡动画消失了，且整个画面没有一张照片，可能是背景残留没有渐出**

- 已回退 `CameraScreen.kt` L367 vfTop 和 `CaptureTransitionOverlay.kt` L227 fromTop 到原始公式

### 修复 1：灵动岛偏下 —— 用实际布局高度代替 configuration.screenHeightDp
**根因**：设置界面（`DynamicIslandSettingsActivity`）用 `BoxWithConstraints.maxHeight`（实际布局高度 px）计算灵动岛位置，而 `CameraScreen` / `CaptureTransitionOverlay` 用 `configuration.screenHeightDp`。两者在 edge-to-edge + hideStatusBar 下通常一致，但某些设备/窗口模式下 `screenHeightDp` 可能包含系统栏区域而实际布局区域不包含 → `posY * screenH` 偏大 → 灵动岛偏下。

**修复**：
- `CameraScreen.kt`：添加 `layoutW` / `layoutH` state（初值 = `configuration.screenWidthDp/HeightDp`），在 outermost Box 上用 `onSizeChanged` 更新为实际布局尺寸（px / density = dp）。`screenW` / `screenH` 改为引用 `layoutW` / `layoutH`
- `CaptureTransitionOverlay.kt`：同样添加 `layoutW` / `layoutH`，outermost Box 上用 `onSizeChanged` 更新。`screenW` / `screenH` 引用 `layoutW` / `layoutH`
- 首帧用 configuration 值（可能偏几 dp），`onSizeChanged` 在首次布局后立即触发修正——差异通常 ≤ 状态栏高度（~24dp），posY=0.06 时偏移 ≤ 1.5dp，用户无感

### 修复 2：预览照片顶部突兀渐变 —— 降低 scrim alpha + 双层叠加
**根因**：浅色模式 scrim 用 `monetColor.copy(alpha = 0.9f)`，90% 不透明完全遮盖模糊背景层。莫奈色（照片主色）与相机页背景（奶油白 `#F0EDE6`）色差大，fadeIn 过程中从透明渐变到 90% 莫奈色显得突兀。

**修复**（`CaptureTransitionOverlay.kt`）：
- scrim alpha 从 `0.9f` 降到 `0.5f`，让模糊背景层柔和透出
- scrim Box 内浅色模式新增双层叠加：`AppBgColor.copy(alpha = 0.3f)`（奶油白半透明），与深色模式的双层结构一致

### 修复 3：退出预览后背景残留 —— 模糊层改用 AnimatedVisibility
**根因**：模糊背景层用 `if (showDetail)` 条件渲染，`showDetail=false` 时立即消失（无淡出动画）。而 scrim 用 `AnimatedVisibility`（有 250ms fadeOut）。两者不同步 → 模糊层瞬间消失但 scrim 还在淡出 → 视觉上"背景残留"或突兀跳变。

**修复**（`CaptureTransitionOverlay.kt`）：
- 模糊背景层从 `if (showDetail) { AsyncImage(...) }` 改为 `AnimatedVisibility(visible = showDetail, enter = fadeIn(250), exit = fadeOut(250)) { AsyncImage(...) }`
- 模糊层与 scrim 同步淡入/淡出，退出预览时平滑过渡

- `CaptureTransitionOverlay.kt`：`layoutW`/`layoutH` state + `onSizeChanged` + scrim alpha 0.9→0.5 + 浅色双层叠加 + 模糊层 AnimatedVisibility + `onSizeChanged` import

## 第二十轮：模糊层底部的黑色元素修复

### 用户反馈
"模糊层底部的背景层有奇怪的黑色元素，随着预览模式出现与消失"

### 根因（两个）
1. **CaptureTransitionOverlay 最外层 Box `background(Color.Transparent)`**：如果模糊层 AsyncImage 在某些区域加载延迟（特别是底部），透出 Android 系统黑色（`Theme.Material` 默认 windowBackground 是黑色）
2. **顶部常驻灵动岛 `if (g > 0.001f)`**：grow 完成后 g=1 持续显示（`IslandShellColor = Color.Black`），close() 时（closing=true）不淡出，直到 onExit 后 overlay 卸载——这 450ms 期间屏幕顶部显示黑色小岛

### 修复
- **`CaptureTransitionOverlay.kt` 最外层 Box `background(Color.Transparent)` → `background(if (isDark) Color(0xFF242424) else Color(0xFFF0EDE6))`**：用 bgColor 覆盖整个屏幕，模糊层加载延迟时不会透出 Android 黑色
- **`CaptureTransitionOverlay.kt` 顶部常驻灵动岛 `if (g > 0.001f)` → `if (g > 0.001f && !closing)`**：close() 时立即不渲染，配合模糊层 + scrim 渐出，顶部小岛也消失

### 验证
`./gradlew compileDebugKotlin` → `BUILD SUCCESSFUL`

### 关键不变量
- CaptureTransitionOverlay 最外层 Box 用 bgColor 覆盖（不是 Transparent）
- 顶部常驻灵动岛 closing 时立即隐藏

- scrim 浅色 alpha = 0.9，模糊半径 = 35f * densityPx（保持）

### 经验教训
- **`Color.Transparent` 背景的隐患**：如果下面的内容（Android window background）不是预期的颜色，会出现"奇怪的黑色/白色"透出。CaptureTransitionOverlay 应该用 bgColor 覆盖整个屏幕，确保视觉一致性。
- **`if (g > 0.001f)` 类型的条件渲染缺少 closing 保护**：`closing` 状态在 close() 入口设为 true，**所有** showDetail 期间显示的元素都应该检查 `!closing`，否则会在 close() 期间残留直到 overlay 卸载。设计模式：**所有"预览模式期间显示"的元素都加 `!closing` 条件**。
- **outermost Box 不能用 bgColor（不透明）覆盖整个过渡期**：会让相册在 morph/hold/extend/emit 阶段就被遮挡。正确做法是 outermost 保持 `Color.Transparent`（相册透出），把 bgColor 底色放进 scrim 内部（只在 showDetail 期间生效）——这样 showDetail 之前相册可见，showDetail 之后由 scrim 遮挡（设计预期）。
- **"文字长度变化导致按钮宽度变化"是 Row 内文字按钮的常见问题**：直接用 `Text + Modifier.clickable` 时，Text 宽度 = 文字宽度，切换文字内容会让整行重排（其他按钮位置也会移动）。修法：用 `Box(width=固定, height=固定, contentAlignment=Center) { Text(maxLines=1) }` 包裹，让按钮成为固定尺寸的"chip"，文字在内部居中。这样切换文字时按钮外尺寸不变，Row 不重排。
- **多选栏所有元素固定宽高 + maxLines=1**：取消(48×36)、已选计数(72×36)、全选(72×36)、分享(72×44)、删除(72×44)。多屏适配靠 dp 自动缩放（Compose 的 dp 会乘以 density），`maxLines=1` 防止文字在小屏换行撑高。Spacer 用固定 dp 间距（8/12dp）。分享/删除胶囊之前用 `padding(horizontal=20.dp)` 撑宽度——文字变化时宽度会变，改为固定 `width(72.dp)` + 移除 padding。
- **多选栏左右间距**：Row 加 `.padding(horizontal = 24.dp)` 在 clip/background 之前——这样胶囊整体与屏幕左右边缘保持 24dp 距离。
- **headerDrag 必须在 effectsExpanded 时禁用**：空相册时 empty state Box 的 `headerDrag`（pointerInput + detectVerticalDragGestures）可能拦截触摸事件导致 EffectsPanel 打不开。修法：`pointerInput(selectionMode, effectsExpanded)` + `if (!selectionMode && !effectsExpanded)`——effectsExpanded 为 true 时禁用 headerDrag，让 EffectsPanel 独占触摸。
- **模糊层用 animateFloatAsState 而非 AnimatedVisibility**：`AnimatedVisibility` + `graphicsLayer { renderEffect = BlurEffect }` 一起用时，alpha 动画可能不生效（renderEffect 可能绕过 AnimatedVisibility 的 alpha 控制）。修法：用 `animateFloatAsState` 控制 alpha，在同一个 `graphicsLayer {}` block 内同时设 `alpha = blurAlpha` 和 `renderEffect = BlurEffect(...)`——两者同层，alpha 动画正确作用于模糊后的内容。`if (blurAlpha > 0.01f)` 条件避免 alpha=0 时仍渲染。
- **EffectsPanel 必须在 if/else 外部**：之前 EffectsPanel 在 `if (photos.isEmpty()) { ... } else { ... EffectsPanel ... }` 的 else 块内——空相册时 else 不执行 → 面板不渲染。用户反馈"图标变了但面板没出现"就是这个原因。修法：移到 if/else 关闭后、Box(weight) 关闭前，并传 `modifier = Modifier.fillMaxSize()` 确保有空间渲染。
- **多选栏删除按钮改圆形图标**：参考 PhotoViewerActivity 的删除按钮——`Box(size=44.dp, clip=CircleShape, background=RetroRust.copy(0.15f)) { Icon(Icons.Filled.Delete, tint=RetroRust) }`。之前是 72dp 宽胶囊 + "删除"文字。
- **预览 zoom 被 clearCaptureRequestOptions 清掉**：`onPreviewStreaming()` 中先 `setZoomRatio` 再 `pushCameraOptions()`，而 `pushCameraOptions()` 内部调 `c2.clearCaptureRequestOptions()` 可能清掉 zoom 设置 → 预览变 1x 但拍照仍正确（拍照时 zoom 重新应用）。修法：把 `setZoomRatio` 移到 `pushCameraOptions()` 之后。
- **FILL_CENTER vs FIT_CENTER**：取景框是正方形（340×340dp），相机传感器是 4:3。`FILL_CENTER` 把 4:3 预览裁切填满正方形 → 预览看起来比实际 zoom 更"放大"（约 1.33x），拍出来的照片是 4:3 全画幅无裁切 → "预览倍率比拍出来的大"。改 `FIT_CENTER`：预览完整显示（不裁切），预览倍率与拍照一致，上下黑边融入取景框黑色背景。
- **拍照 1:1 裁切（WYSIWYG）**：用户要求"拍出的照片要裁切成1:1"——恢复 `FILL_CENTER`（预览裁切到正方形），在 `PhotoStorage.addPolaroidFrame` 中 EXIF 旋转后、滤镜前加 1:1 中心裁切：`minOf(w,h)` 取短边，居中裁切。这样预览（FILL_CENTER 中心裁切）和拍照（1:1 中心裁切）完全一致——所见即所得。
- **多选栏尺寸计算**：Row 总宽度必须 < 屏幕宽度，否则 `size(44.dp)` 的圆形删除按钮会被挤压变形。计算：取消(40) + 间距(8) + 已选(52) + 间距(4) + 全选(60) + 间距(8) + 分享(60) + 间距(8) + 删除(44) = 284dp + 内边距(32) + 外边距(32) = 348dp < 360dp（最窄屏）。留 12dp 余量确保不溢出。
- **多选栏浅色背景对比度**：相册背景 `Color(0xFFF0EDE6)`（冷白偏米色）与 `surfaceCard = RetroCream (0xFFF5EDE2)` 几乎相同，胶囊"消失"在背景中。修法：浅色模式用 `RetroPaper (0xFFEDE0C8)` 替代——暖黄牛皮纸色与冷白背景形成明显对比，保留复古胶片调性（暖色调）。深色模式 `surfaceCard (0xFF2E2E2E)` 与背景 `0xFF242424` 已有对比，保持原样。
- **降饱和度具体值**：RetroPaper (0xFFEDE0C8) 饱和度 ~58%，看起来太黄。降到 0xFFEAE3D5（饱和度 ~35%），保留暖色调但与背景对比更柔和不抢眼。如果还不够，可以进一步降到 0xFFE8E0D0（饱和度 ~25%）。
- **scrim 莫奈色被稀释问题**：之前 scrim Box 底色 = bgColor (0xFFF0EDE6 浅色 / 0xFF242424 深色)，内层 scrimColor = monetColor.copy(alpha=0.9) 在浅色模式——结果 90% 莫奈 + 10% bgColor 透出，10% 浅米色把莫奈"洗"淡了。修法：浅色模式 scrim Box 底色直接用 `monetColor`（全不透明莫奈）替代 bgColor，移除内层 scrimColor——莫奈 100% 呈现，bgColor 不再稀释莫奈。深色模式保留原结构（底色 + 多层 scrim/monet/灰遮罩）。AnimatedVisibility 淡入淡出仍然作用于整个 scrim Box。
- **莫奈取色发灰的根因**：`Palette.getLightMutedColor` 对暖色 vibrant 照片经常拿不到对应 swatch（warm photos 通常只有 vibrant swatch，没有 light muted）→ 总是回退到 fallback（浅米色）→ 再叠 `desaturate(0.55)` → 结果就是单调灰。修法：改用 `getDominantColor`（按像素出现频率取最显著色）作为首选，回退链 Dominant > Vibrant > LightVibrant > Muted > fallback。同时降低 desaturate factor 0.55 → 0.25（保留色调），加 `lighten=0.35`（避免暗照片背景过暗）。
- **取色 swatch 最终方案 getLightVibrantColor > getDominantColor > fallback**：经历了多轮迭代——
  - 最初 `getLightMutedColor`：对屏幕照片/暖色 vibrant 照片经常拿不到 swatch → 总回退
  - 改为 `getDominantColor`：对夕阳照片取到暗色建筑轮廓（dominant = 最频繁色 = 建筑剪影）→ 背景变深棕
  - 最终 `getLightVibrantColor` 为主、dominant 为 fallback：优先取亮色主调（夕阳天空、暖色物体），无 light vibrant swatch 时退到 dominant（屏幕白底等）
- **取色修改边界**：两处必须同步——`CaptureTransitionOverlay.extractDominantColor` 和 `PhotoViewerActivity.extractDominantColor` 使用相同的 swatch 链 + 相同的 `RetroPaper.toArgb()` fallback，确保预览和详情页背景色完全一致。
- **预览 scrim 与详情页取色一致性**：取色函数完全一致后，背景应用方式为——浅色模式 scrim = `monetColor.copy(alpha = 0.9f)`（与详情页 `bgColor` 取色相同但 90% 不透明，用户明确要求 0.9f）；深色模式 scrim 结构与详情页一致（底色 RetroDarkBg + monetColor 0.4 + 灰遮罩 0.6）。详情页浅色模式是 100% 不透明 `bgColor`，预览是 90% 不透明——这是预览为了透出一点底层动画/相册的折中。
- **取色时序：必须等 addPolaroidFrame 完成且文件 flush**：之前 `LaunchedEffect(file) { extractDominantColor(...) }` 立即执行——但此时 `CameraViewModel.addPolaroidFrame` 正在用 `FileOutputStream` 截断+重写同一个文件！`extractDominantColor` 读到的是残缺文件，Palette 解析出错取到错误色调（如暖色照片取到冷色）。详情页取色是用户点入后才执行，那时文件已完整，所以详情页正常。**最终修法**：把取色逻辑移到 ViewModel 的 `addPolaroidFrame` 协程内——`addPolaroidFrame` 返回后**同一 IO 线程**立即调 `PhotoStorage.extractDominantColor`，结果通过 `_extractedColor` StateFlow 传给 overlay。彻底消除 overlay 读取时机/OS 缓存问题。共享取色函数放在 `PhotoStorage.extractDominantColor`，`PhotoViewerActivity` 也改用同一函数。
- **scrim 结构必须与详情页逐层对齐**：之前深色模式多了一层 `scrimColor`（Color(0xFF242424).copy(0.92)），虽然颜色与底色相同看似无影响，但用户反馈"取色展示不一致"——可能 Compose 多层 alpha 叠加有微小色差。修法：逐层移除，深色模式只保留 `底色 + monetColor(0.4) + 灰遮罩(0.6)` 三层，与 PhotoViewerActivity 完全一致。
- **灵动岛 close() 期间消失再出现**：根因是 `shellAlpha = if (e < 1f) 1f else (1f - g)`——close() 时 g=1 → shellAlpha=0 → 灵动岛 shell 立即消失，但 ViewfinderFrame 要等 onExit（transitionFile=null）才显示 → 中间有"空窗期"。修法：`shellAlpha = if (closing) 1f else if (e < 1f) 1f else (1f - g)`——close() 期间 shellAlpha=1，shell 停留在 shrink 后的岛位置（isLeft/isTop/isW/isH），与 ViewfinderFrame 在 p=0 的岛视觉无缝衔接。

## 第二十二轮：取景框预览倍率异常放大（WYSIWYG 修复）

### 问题
取景框内预览画面比实际拍出的照片"放大很多"（预览视野更窄），但成片正常。

### 数据流核对（WYSIWYG 边界）
- 预览：`PreviewView`（`scaleType = FILL_CENTER`）+ 4:3 缓冲 → 中心裁切填满正方形取景框
- 成片：`PhotoStorage.addPolaroidFrame` → `side = minOf(w,h)` 严格 1:1 中心裁切
- 两者在"4:3 缓冲 + 正方形框"下裁切区域完全一致 → 应为所见即所拍
- `controller.setZoomRatio` 是相机共享控制，预览/成片同倍率，不存在"仅预览被放大"

### 关键根因（用户纠正）
**`AndroidView` 上加 `padding((borderDp * progress).dp)` 是错误的**：
- `FILL_CENTER` 的缩放 = `max(viewW/bufW, viewH/bufH)`，依赖 PreviewView 当前尺寸
- padding 把 PreviewView 缩小 → CameraX 重新算 scale → **二次裁切** → 预览比成片更放大
- 且 `progress` 在展开动画 0→1 每帧变化 → PreviewView 尺寸每帧变 → 预览内容不断重缩放（视觉"越来越放大"）
- `Modifier.border` 是 **draw 层**，不占布局空间（不会缩小 PreviewView），黑边只是最后画一层覆盖外缘

### 修复
- `ViewfinderFrame.kt`：`AndroidView` modifier 改回 `Modifier.fillMaxSize()`（**去掉 padding**）
- `ViewfinderFrame.kt`：移除 `progress: Float` 参数（不再用于内缩），同步移除 `padding` import 与 `CameraScreen.kt` 的 `progress = p` 调用
- `ViewfinderFrame.kt`：`implementationMode = COMPATIBLE`（保留原值，TextureView 可被 Compose `clip(RoundedCornerShape)` 裁圆角）
- `CameraViewModel.kt`：保留 `setPreviewResolutionSelector/setImageCaptureResolutionSelector(4:3)`（强制 4:3 缓冲，FILL_CENTER 裁切量最小）
- 黑边维持 draw 层 `Modifier.border` 覆盖绘制（用户推荐的"正确做法一"）

### 验证
`./gradlew compileDebugKotlin --rerun-tasks` → `BUILD SUCCESSFUL`（仅无关 warning）

### 经验教训
- **FILL_CENTER 与 Compose padding 不是同一坐标系**：任何改变 PreviewView 尺寸的 layout 操作都会让 FILL_CENTER 重算缩放 → 二次裁切。要缩小可见预览，必须用 `graphicsLayer { clip }` / `clipRect` 去裁"已渲染的像素"，而不是缩小 View 本身。
- **动画期间的 View 尺寸变化是隐性 bug 源**：morph 动画若用 progress 驱动 padding/scale 等 layout 属性，每帧触发重新测量+CameraX 重算，表现像"持续 zoom"。保持 PreviewView 尺寸恒定（fillMaxSize）最稳。
- 黑边用 draw 层 border（不占空间）而非 padding（占空间）这条项目约定必须守住——既保证折叠态 Surface 非零能 STREAMING，也避免 FILL_CENTER 二次裁切。

## 第二十三轮：取景框预览严重过放大（~2.8×）—— 根因是 LifecycleCameraController 的 hint 被默认屏幕分辨率覆盖

### 问题
取景框内预览比成片"放大很多"（远大于 1.27×），即使加了 `setPreviewResolutionSelector(4:3)` 也没用。

### 根因（从 CameraX 官方文档查到）
`LifecycleCameraController` 的 `setPreviewResolutionSelector` 等方法只是 **hint**，官方文档明确说：
> "CameraX uses this value as a hint... The actual output may differ from the requested value due to device constraints. **By default, the selected resolution will be limited by the PREVIEW size which is defined as the best size match to the device's screen resolution, or to 1080p (1920x1080), whichever is smaller.**"

手机屏幕 ~1080×2400（9:20），所以预览实际用的是 9:20 缓冲；成片是 4:3 传感器的 1:1 中心裁切。FILL_CENTER 把 9:20 缓冲裁成 1:1 → 显示的源像素 ~1080×1080；成片中央 3000×3000 源像素。过放大 ≈ 3000/1080 ≈ 2.8×。

`setTargetAspectRatio` 在 `LifecycleCameraController` 上**已不存在**（1.4.2 移除），所以快捷方法也走不通。

### 修复：放弃 LifecycleCameraController，改用 ProcessCameraProvider 直接绑定自定义 use case
**`CameraViewModel.kt`**：新增 `preview` / `imageCapture` 字段（`.setTargetAspectRatio(AspectRatio.RATIO_4_3).build()`，硬约束在 use case 上不被默认覆盖），新增 `bindCameraUseCases(owner)` 异步等 `ProcessCameraProvider` 就绪后 `bindToLifecycle`。`setZoom` / `restoreZoom` / `onPreviewStreaming` / `pushCameraOptions` / `switchCamera` 全部改用 `boundCamera?.cameraControl`。

**`ViewfinderFrame.kt`**：参数从 `controller: LifecycleCameraController` 改为 `preview: Preview` + `bindCameraUseCases: (LifecycleOwner) -> Unit`。factory 块里 `preview.setSurfaceProvider(this.surfaceProvider)` 把 PreviewView 的 surface 接到 Preview use case，然后调 `bindCameraUseCases(lifecycleOwner)`。

**`CameraScreen.kt`**：传 `preview = vm.preview, bindCameraUseCases = vm::bindCameraUseCases`。

### 效果
- 预览和拍照共用同一组 `preview` + `imageCapture` use case，**同一缓冲**（都是 4:3）
- FILL_CENTER 把 4:3 裁成 1:1 = addPolaroidFrame 中心 1:1 裁切
- 严格 WYSIWYG

### 经验教训
- **CameraX 的 hint 不可靠**：`setPreviewResolutionSelector` / `setPreviewTargetSize` / `setImageCaptureTargetSize` 都是 hint，会被默认屏幕分辨率覆盖
- **use case 的 `setTargetAspectRatio` 是硬约束**：在 `Preview.Builder()` / `ImageCapture.Builder()` 上调用，不被默认覆盖，但 `LifecycleCameraController` 在 1.4.2 已移除便捷 setter
- **需要硬约束时直接用 `ProcessCameraProvider` + 自定义 use case**，不要依赖 `LifecycleCameraController` 的 hint
- 用户提示"先试 2 不行再 1"是正确决策：先 `setTargetAspectRatio(controller)` 快速试，不行再大改
